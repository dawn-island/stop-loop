# stop-loop — Claude Code 플러그인

카드 한 장을 열세 단계(분석 → 범위 검증 → 질문·답변 → 설계 → 설계 검증 → 시험 먼저 구현 → 품질 확인 → 검토 → 인계 → 회고)로
돌리는 워크플로우다. 검토 단계는 기본으로 꺼져 있고 설정 `reviewPolicy` 로 켠다. 단계마다 새 세션이 앞 단계의 산출물만 보고 일하고, 검증 단계는 만든 쪽과 다른 에이전트가 맡는다.

## 미리 필요한 것

| 무엇 | 확인 | 비고 |
|---|---|---|
| Claude Code | `ls ~/.local/bin/claude` | 러너가 이 경로를 직접 부른다 |
| python3 | `python3 --version` | 표준 라이브러리만 쓴다 |
| git 2.44 이상 | `git --version` | 카드마다 워크트리를 연다 |
| gh | `gh auth status` | 인계를 PR 로 할 때만 |
| rg (ripgrep) | `rg --version` | 선택 — 문서 검색에 먼저 쓴다. 없으면 `grep` 으로 돈다 |

## 설치

```bash
claude plugin marketplace add dawn-island/stop-loop
claude plugin install stop-loop@stop-loop
```

판을 올릴 때는 `claude plugin update stop-loop@stop-loop`. 실행 도중 판이 바뀌면 러너가 다음 단계 앞에서 멈추고,
`--resume` 으로 이어받는다.

## 프로젝트에 세우기

프로젝트 뿌리에서 Claude Code 를 열고:

```
/stop-loop:setup
```

만들거나 고치는 것 — 커밋은 하지 않는다:

- `CLAUDE.md` — 없으면 틀로 만든다. 있으면 표준 구간만 바꾼다. `<…>` 자리표시(시험 명령, 실행하지 않을 명령, 신원 등)는 직접 채운다.
- `stop-loop.config.json` — **`checks` 를 이 프로젝트의 시험 명령으로 고친다.** 비워 두면 시험 없이 구현 단계를 통과한다.
- `testPaths` (선택) — 구현 단계 게이트가 「시험 파일」로 치는 경로 낱말 목록. 기본값은 `["test", "spec"]`.
  경로 어디에든(대소문자 무시) 그 낱말이 들어 있으면 시험 파일로 센다 — `test` 는 `latest/` 도 잡는다.
  `.md` 로 끝나는 파일은 낱말이 있어도 세지 않는다. 셸 확인 스크립트를 시험으로 치려면
  `"testPaths": ["test", "spec", ".check.sh"]`. 게이트가 「테스트를 건드린 커밋이 없다」로 막히면 문구에 지금 낱말이 보인다.
- `checks` 줄의 `paths` (선택) — 이 카드가 바꾼 파일 가운데 하나라도 맞을 때만 그 줄을 돌린다. 항목은 경로 앞부분
  (`web/`)이나 글롭(`shared/**`). 없으면 늘 돈다. 바뀐 파일을 알 수 없으면 돈다. 건너뛴 줄은 터미널에
  「건너뜀 — 바뀐 파일이 paths 에 없다」로 남는다. 예: `{"cmd": "pnpm test:web", "paths": ["web/", "shared/**"]}`
- `docs/backlog/_템플릿.md` — 카드 틀. 머리말 `기능:` 칸에 그 카드가 건드리는 기능 ID(예 `F-012, F-013`)를 쉼표로 적는다. 비워도 된다.
- `docs/기능맵/README.md` — 기능 목록 설명서(칸 쓰는 법과 그룹 파일 머리 모양). `docs/기능맵.md` 도 `docs/기능맵/` 도 없을 때만 만든다. 있으면 건드리지 않는다. 기능은 `docs/기능맵/<그룹>.md`(파일 하나가 기능 그룹 하나, `F-ddd` 는 프로젝트 전체에서 하나)에 적는다. 옛 한 장 `docs/기능맵.md` 도 그룹 하나로 함께 읽는다. 있으면 01 분석과 05 설계가 전체를 읽지 않고 기능 ID 마다 입력에 실린 자리에 `rg -n "F-012" docs/기능맵/` 로 그 줄과 그 ID 를 가리키는 줄만 조회한다.
  옛 한 장을 그룹 파일로 나누는 법: 줄을 그대로 `docs/기능맵/<그룹>.md` 로 옮기고 ID 는 바꾸지 않으며, 옮긴 줄은 옛 파일에서 지운 뒤 `featuremap_check.py` 를 돌린다.
  정본 규칙: 구현된 기능의 정본은 코드와 기능맵, 계획 중인 기능의 정본은 시나리오(`docs/plan/SC-*.md`)다.
  기능맵이 있으면 07 구현 관문이 검사 넷(ID 겹침 · 관련 기능이 없는 ID · 「구현됨」 줄의 코드·시험 위치 파일 · 소스 머리 주석)으로 막고 어긋난 줄을 보인다.
  머리 주석 형식: 소스 파일 앞 10줄 안에서 주석 기호 뒤에 `기능: F-012` 한 줄. 그 ID 가 기능맵에 있고 그 파일이 그 줄의 코드 위치에 있어야 한다(`.md` 는 보지 않는다).
  손으로 돌리기: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/featuremap_check.py" .` (기능맵 없음·통과 0, 어긋남 1)
  기존 기능 채우기: `/stop-loop:featuremap <폴더 경로 또는 시나리오 번호>` — 그 범위를 조사해 줄을 덧붙이고 검사를 돌린다. 커밋은 하지 않는다. 범위를 안 주면 묻는다.
- `.claude/settings.json` — 이 플러그인 선언.

GitHub 계정이 여럿이면 설정에 `"githubAccount": "<계정>"` 을 넣는다. 러너가 그 계정의 토큰만 쓰고, 올리기 전에 로그인
계정이 다르면 멈춘다.

## 쓰기

계획이 여러 카드로 나뉘면 시나리오부터(1), 카드 한 장이면 카드부터(2) 한다.

1. **시나리오를 쓰고 승인한다 — 사람이 깊이 관여하는 자리는 여기다.** 프로젝트 뿌리에서:

   ```
   /stop-loop:scenario
   ```

   스킬이 `docs/plan/SC-<번호>.md` 초안과 요소 카드 초안(`상태: 아이디어`)을 함께 만들고, 승인 전 점검 결과를 보여 준다.
   됐다고 하면 시나리오의 `상태` 를 「확정」으로 바꾼다. 승인은 시나리오와 카드 초안을 함께 한다.
   그다음 배차를 띄운다:

   ```
   /stop-loop:dispatch
   ```

   배차가 승인을 판정해 앞선 카드가 없는 카드부터 대기로 올리고, 대기 카드를 집어 러너로 돌린다. 동시에 도는 카드는 이 기기에서 기본 4 장까지이고,
   `~/.stop-loop/projects.json` 맨 위에 `"maxParallel": <1 이상 정수>` 를 적으면 그 값으로 바뀐다. 같은 프로젝트의 카드도 함께 돌되,
   카드 본문 「## 시작점」에 적힌 저장소 경로가 돌고 있는 카드와 하나라도 같으면 그 카드가 끝날 때까지 기다린다(경로가 없으면 겹침으로 보지 않는다. 「고치는 파일」 줄이 있으면 그 줄의 경로만 본다). 조건을 채운 PR 은 러너가 병합하고,
   병합되면 다음 카드가 대기로 오른다. 더 돌 것이 없으면 배차는 스스로 끝난다. 마지막 카드가 끝나면 완료 보고서(`docs/plan/끝보고-SC-<번호>.md`)가 생기고,
   사람이 그것을 보고 시나리오 상태를 「완료」로 바꿔 완료를 선언한다.
   승인한 뒤 고칠 때는 상태를 「초안」으로 내렸다가 고친 다음 「확정」으로 다시 올린다.

   **상주 배차** — 위의 배차는 더 돌 것이 없으면 스스로 끝난다. 사람이 띄우지 않아도 대기 카드를 집게 하려면 끝나지 않는 `--상주` 로 띄운다:

   ```
   python3 "<플러그인 폴더>/scripts/dispatch.py" --상주          # 끝나지 않는다 — 터미널에서 띄워 두기
   python3 "<플러그인 폴더>/scripts/dispatch.py" --상주-켜기     # 로그인 때 저절로 뜨게 등록(PATH 포함)
   python3 "<플러그인 폴더>/scripts/dispatch.py" --상주-끄기     # 등록 해제
   ```

   60초마다 한 바퀴를 돈다. 바퀴마다 `~/.stop-loop/projects.json` 의 `"projects"` 를 다시 읽고(`"보기"` 와 `projects.yaml` 은 읽지 않는다), 프로젝트마다
   원격의 기준 가지를 빨리감기로만 받고(작업 사본이 기준 가지에 있고 커밋 안 된 변경이 없거나 카드 기계 열쇠 줄뿐일 때만 — 아니면 받지 않고 까닭을 남긴다),
   병합된 `검토` 카드를 `완료` 로 정리하고, 대기 카드를 집는다. 시작점이 겹치는 앞 카드의 PR 이 열려 있으면 뒤 카드는 PR 이 병합될 때까지 집지 않는다.
   기기 지정(카드 `기기:` 칸과 프로젝트 `"기기"`)은 그대로 지킨다.
   - **멈추는 법**: `~/.stop-loop/dispatch.stop` 파일을 만들면 새 카드를 집지 않고 도는 러너만 끝까지 지켜본 뒤 쉰다. 파일을 지우면 다음 바퀴부터 다시 집는다.
   - **살아 있음 파일**: `~/.stop-loop/status/dispatch.json` 에 이 기기 이름·마지막으로 쓴 때·바퀴·돌고 있는 카드·건너뛴 까닭을 쓴다. 보드 사이드바가 이것으로 「배차 켜짐 · 마지막 바퀴 N분 전 / 꺼짐」을 보인다.
   - **판이 바뀌면**: 상주 배차가 자기 판과 설치된 판이 다른 것을 보면 새 카드를 집지 않고 쉬며(옛 판 러너를 띄우지 않으려는 것) 사이드바에 알린다. 새 판 폴더의 `scripts/dispatch.py --상주-켜기` 로 다시 켠다.
2. **카드 한 장만 돌릴 때** — `docs/backlog/<이름>.md` 에 카드를 쓰고(머리말 `상태: 아이디어`, 「사람이 하면 몇 분」과 최소 범위),
   **사람이** `상태: 대기` 로 올린 뒤 `/stop-loop:dispatch` 또는 `/stop-loop:loop <카드 이름>` 으로 돌린다.
   시나리오에 묶이지 않은 카드는 사람만 대기로 올린다 — 러너도 회고도 올리지 않는다.

브리핑을 저장소에 남기려면 `docs/pm/브리핑/` 폴더를 만든다. 폴더가 있는 프로젝트에서만 `/stop-loop:briefing` 이 파일을 저장하고 커밋·push 하며,
`/stop-loop:briefing <날짜 또는 어제>` 로 저장본을 연다. 폴더가 없으면 읽기만 한다. 고객 이름과 독촉 문안이 들어가므로
공개 저장소에서는 켜지 않는다.

PR 본문 맨 위에 판단표와 「사람 결정 미결」이 있다. 자동 병합되지 않은 PR 은 사람이 보고 병합한다.

진행은 보드로 본다 — 사람이 할 일이 맨 위 「내 할 일」에 모인다:

```
/stop-loop:board
```

배차와 보드는 그 기기의 목록 파일 `~/.stop-loop/projects.json` 에 등록된 프로젝트를 본다. `/stop-loop:setup` 이 등록한다. 보기만 할 프로젝트는 그 프로젝트 폴더에서 `python3 "<플러그인 폴더>/scripts/board.py" --연결 .` 한 번으로 올린다(아래).

보드 서버는 기기마다 하나이고 `127.0.0.1:8700` 에만 열린다. 홈에 보는 목록의 모든 프로젝트와 모든 사람 차례가 보이고, 줄을 누르면 그 프로젝트 보드가 열린다.
보드가 쓰는 곳은 이 기기의 보드 전용 자리 셋과 사람이 누르는 단추 셋이다. 보드 전용 자리는 `~/.stop-loop/mirrors/<프로젝트 폴더 이름>.git`(거울), `~/.stop-loop/board-cache/<프로젝트 폴더 이름>.json`(board-cache, 읽은 원격 그림), `~/.stop-loop/human-resolved/<프로젝트 폴더 이름>/`(사람 손 기록)이다. 상주 보드는 프로젝트 작업 사본의 파일·색인·참조·객체를 스스로 바꾸지 않는다. 사본에 쓰는 것은 사람이 누른 단추 셋뿐이다 — 「카드로 만들기」(아이디어 카드 파일 하나를 쓰고 원격 저장소에 올린다), 「카드에 잇기」, 시나리오에 안 묶인 아이디어 카드의 「대기로 올리기」(확인 창 뒤에 `상태:` 줄만 대기로 바꿔 그 파일 하나만 올린다). 단추는 이 기기(127.0.0.1)에서 보드 화면이 보낸 요청만 받는다.
워크플로우 회고(`/retro`, 사이드바 「워크플로우 회고」)는 stop-loop 워크플로우를 고치려고 보는 화면이다 — 기간(이번 주·지난주·30일)과 프로젝트로 거른 여섯 칸이 위에서 아래로 있다: 핵심 지표(카드당 사람 개입·첫 통과율·자동 병합 비율과 막은 까닭·카드당 비용과 시간, 직전 기간 대비), 단계별 표(반려율·평균 시간·예상 대비·이어받기·헛도는 회차, 줄을 펼치면 막힌 카드와 회고의 막힌 자리), 멈춤 원인(`멈춘종류:` 별 수·사례·처방), 반복 지적에서 규칙까지(회고 제안의 채택·반영·효과 확인), 바꾼 것의 효과(`workflows/metrics/워크플로우-변경.md` 줄의 전후 값과 판정), 이 기간의 회고(소각된 실행의 `11-retro.md` 전문). 기록이 없는 칸은 「—」와 「기록이 아직 없음」이다. 읽기만 하며, 쓰기는 개선 후보와 같은 「카드로 만들기」 길 하나뿐이다.
`/stop-loop:board` 는 새 서버를 띄우지 않고 그 주소를 알린다(떠 있는 보드가 없을 때만 띄운다).

- 로그인 때 저절로 뜨게 켜기: `python3 "<플러그인 폴더>/scripts/board.py" --상주-켜기`, 끄기: `--상주-끄기`. **플러그인 판이 바뀌면 상주를 다시 켠다** — 로그인 항목은 켠 때의 판 경로를 가리킨다. 이미 상주를 켠 사람은 이 판으로 `--상주-켜기` 를 **한 번 다시** 해야 등록 파일에 켜는 순간의 PATH(`gh`·`git` 폴더)가 들어간다 — 로그인 자동 실행의 기본 PATH 에는 `/opt/homebrew/bin` 이 없어 PATH 가 없는 등록 파일에서는 원격을 읽지 못한다.
- 프로젝트를 보드에 연결하기: 그 프로젝트 폴더에서 `python3 "<플러그인 폴더>/scripts/board.py" --연결 .` (`/stop-loop:board` 스킬의 「이 프로젝트를 대시보드에 연결」 절도 이것을 부른다). 올리기 전에 원격(origin)이 있는지, `handoff` 가 `local` 이 아닌지, GitHub 계정(`githubAccount`)으로 원격을 읽을 수 있는지 확인해 까닭과 고칠 값을 찍는다. 기본은 보기만 하는 목록(`"보기"`)에 올리고 배차는 집지 않는다. 배차까지 맡기려면 `--배차`, 기기 이름을 적으려면 `--기기 <이름>` 을 더한다. 이미 올라 있으면 목록 파일을 바꾸지 않는다. 확인에 걸린 프로젝트는 보드 사이드바에 「연결 확인 — 까닭 — 고칠 값」 줄이 뜨고 홈 「손볼 것」 칸 설명에 「연결 확인 N곳」이 붙는다. 프로젝트의 `stop-loop.config.json` 을 고쳐 push 하면 다음 읽기에 풀린다.

카드별 시간·비용을 모아 보려면 프로젝트 뿌리에서(소각 커밋이 없으면 「소각 커밋 없음」):

```
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/runcost.py" <프로젝트 경로>
```

## 보드는 원격을 출처로 본다 · 거울 자리 · 디스크 · 끊겼을 때 보이는 것

진짜 기록은 GitHub 원격이다. 보드는 작업 사본이 아니라 프로젝트마다 둔 **거울**(보드 전용 bare 저장소, 작업 파일이 없는 git 저장소)에서 카드 목록·상태·본문, 시나리오 문서, 소각 커밋(시간·비용·회고)을 읽는다. 작업 사본이 뒤처지거나 고친 파일이 있어도 보드의 카드 상태는 원격과 같다.

- **거울 자리**: `~/.stop-loop/mirrors/<프로젝트 폴더 이름>.git`. 원격의 기준 가지를 `refs/remotes/origin/<가지>` 이름표로 받아 둔다. 처음 만들 때는 그 기기에 있는 작업 사본의 객체를 복사해 쓰므로(`--reference` + `--dissociate`) 큰 저장소를 다시 내려받지 않는다. 만든 뒤 거울은 사본과 이어져 있지 않다.
- **확인과 받기**: 1분마다 프로젝트마다 `git ls-remote` 한 번으로 원격 끝을 본다. 끝이 앞서 읽은 것과 같으면 받기도 다시 읽기도 하지 않는다. 바뀌었을 때만 거울로 받는다. 프로젝트 설정(`handoff`·`githubAccount`·`stageLimits`)도 원격 끝의 `stop-loop.config.json` 에서 읽는다 — 사본이 뒤처져도 원격 끝의 것을 따른다. 처음 접속하는 계정과 원격에 그 파일이 없을 때만 작업 사본의 설정을 쓴다.
- **board-cache**: `~/.stop-loop/board-cache/<프로젝트 폴더 이름>.json` 에 원격 끝 커밋·카드 상태·마지막으로 받은 때·마지막 시도·실패 까닭을 남긴다. 보드를 다시 띄우면 첫 원격 확인 전에도 이 그림으로 시작하고 사이드바에 「원격 기준 N분 전」이 나온다. 무거운 계산 저장(비용·품질 등)의 열쇠도 원격 끝이다.
- **사람 손 기록**: `~/.stop-loop/human-resolved/<프로젝트 폴더 이름>/사람손-<SC>.md`. 옛 기록과 배차가 쓰는 기록은 사본 `docs/plan/` 에 남아 있어, 보드의 처리 기록과 시나리오 완료 보고서는 두 자리를 모두 읽는다.
- **디스크**: 거울은 프로젝트마다 하나이고 원격의 기준 가지 이력만 든다. 보는 목록에서 뺀 프로젝트의 거울·board-cache 는 지우지 않는다. 폴더 이름이 같은 두 프로젝트를 함께 보면 이 세 자리가 겹친다.
- **다른 기기 카드**: 진행 카드에는 「마지막 소식 N분 전」(원격에서 그 카드 머리말이 마지막으로 바뀐 때부터)이 나오고, 단계 시간 상한보다 오래되면 「소식 끊김 — 돌던 기기 확인」이 「손볼 것」에 한 장으로 센다. 이 기기가 돌리는 카드는 이 기기의 실시간 줄과 러너 생존 경보를 지금처럼 본다.

**끊겼을 때 보이는 것**

- 원격을 못 읽으면 앞서 읽은 그림이 그대로 남고 사이드바에 「원격 저장소를 아직 못 읽음 — <까닭>」과 「원격 기준 N분 전」(5분이 넘으면 「5분 넘게 못 받음」)이 나온다. 거울은 디스크에 있으므로 이력 화면은 계속 읽힌다.
- 처음 띄웠고 board-cache 도 없으면 첫 한 바퀴(최대 1분)는 「원격 읽는 중」이고 카드는 작업 사본 것이다.
- 원격이 없는 프로젝트(origin 이 없음)는 거울을 두지 않고 작업 사본을 읽는다. `handoff: local` 인 프로젝트는 설정을 읽으려고 거울을 두지만 카드·이력은 작업 사본을 읽는다.
- 원격이 있는 프로젝트에서 작업 사본에만 있는 카드는 보이지 않는다. 사라진 것이 아니라 아직 원격에 올라가지 않은 것이다.
- 보드 서버가 내는 `plan/`·`todo/` 문서와 한 번 찍기(`--한번`)가 쓰는 `board.html` 은 작업 사본의 것이다. 사본이 뒤처지면 뒤처진 채로 보인다.

## 여러 기기에서 쓸 때

같은 저장소를 MacBook 과 Mac mini 에 등록하면 배차는 기기와 상관없이 대기 카드를 집는다. 카드를 기기별로 나누려면 두 군데에 이름을 적는다.

- 카드 머리말에 `기기: Mac mini` 를 적는다. 비었거나 `—`·`-` 이면 어느 기기나 집는다.
- 그 기기의 `~/.stop-loop/projects.json` 프로젝트 항목에 `"기기": "Mac mini"` 를 사람이 적는다. 칸이 없으면 지금처럼 모든 카드를 집는다.

```json
{"name": "myapp", "path": "~/myapp", "기기": "Mac mini"}
```

- 카드 `기기:` 와 목록 파일 `"기기"` 가 다르면 그 카드는 집지 않고 상태도 바꾸지 않는다. 다른 기기에서 도는 「진행」 카드는 이 기기를 막지 않고, `선행` 판정은 기기와 상관없이 모든 카드를 본다.
- 이름은 정확히 같아야 한다. 오타(`Macmini`)면 어느 기기에서도 안 집히고, 배차 끝 줄 「건너뜀」에 `프로젝트(다른 기기 카드만 남음)` 으로만 보인다.
- `/stop-loop:setup` 은 기기 이름을 묻지 않는다. 다시 등록해도 기존 `"기기"` 칸은 지워지지 않는다.

### 이 기기의 이름 한 자리

`~/.stop-loop/projects.json` 맨 위에 `"이 기계": "Mac book"` 을 적으면 러너·배차·카드 배송 도구·보드가 모두 이 이름을 먼저 쓴다. 새 실행의 카드 머리말 `돈기계` 가 이 이름이 되고, 보드의 타임라인은 옛 기록에 호스트 이름으로 남은 이 기기도 같은 레인으로 묶는다. 칸이 없거나 비었으면 지금처럼 배차가 넘기는 `기기`, 그것도 없으면 호스트 이름이다. 이름 없이 남은 옛 기록(「기기 기록 없음」)은 묶지 않는다. 카드 `기기:` 거름과 프로젝트 `"기기"` 의 뜻은 그대로다.

## 워크플로우 개선을 알리기

회고 단계는 워크플로우에서 고칠 것을 「## 워크플로우 몫」(PR 본문 끝)에 적는다.
워크플로우 몫은 이 저장소의 이슈로 모은다. 러너가 PR 을 연 가지(`loop/<카드>`)에서, 프로젝트 뿌리에서:

```
/stop-loop:report
```

1. 먼저 아무것도 올리지 않고 「올릴 문장」을 보여 준다. 회사 정보 검사를 거친 문장이다.
   같은 이슈가 이미 있으면 「댓글을 단다 #번호」로 보여 준다.
2. 사람이 그 문장을 확인했을 때만 스킬이 올린다. 확인이 없으면 올리지 않는다.
3. 「올리지 않는다 — …」 줄은 회사 정보가 걸린 자리다. PR 본문의 그 칸을 고친 뒤 다시 부른다.

커밋은 하지 않는다. 카드 끝에 이슈 주소 한 줄이 더해지면 `git diff` 로 확인하고 커밋은 사람이 한다.

## 이 저장소는 배포판이다

이 저장소는 발행된 배포판이라 PR 을 받지 않는다. 내용은 정본에서 빌드해 옮긴 결과이므로, 여기서 고쳐도 다음 발행이 덮는다.
워크플로우 개선은 `/stop-loop:report` 나 이 저장소의 이슈로 알린다.
